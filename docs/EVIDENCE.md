## Fixture and freshness

`fixtures/evidence_observations.json` has `live_retrieval` false and two synthetic observations.

- `obs-usd-nok-2026-03-31` is USD/NOK, unit NOK per 1 USD, value `10.25`, observed and retrieved `2026-03-31`, provenance `synthetic-fixture-not-a-live-norges-bank-retrieval`. At as-of `2026-03-31` and a maximum age of 7 days it is fresh. The desk says that number matches the ledger's supplied 10.25 rate. The match is not a live source confirmation.
- `obs-stale-policy` is the policy rate, unit percent, value `4.50`, observed and retrieved `2026-01-02`, provenance `synthetic-stale-policy-fixture`. At the same as-of and window it is stale.

A value is a `Decimal` parsed from a string, or `None` when the fixture says the value is missing. JSON numbers are rejected, so a float cannot enter. `NaN`, `Infinity`, and `-Infinity` are rejected as `non_finite` and are not stored as amounts. Dates parse with `datetime.date.fromisoformat`. Whitespace-only provenance is blank, and that observation is not stored.

EVIDENCE-01 treated the same observation id and the same value as one stored row, even when the dates differed. The current rule is narrower. A repeat is a duplicate only when observation id, source, subject, unit, value, observation time, retrieval time, provenance, and quality flags all match. The same id with any other field different, including the same Decimal value and a different observation time, is a conflict. Both observations stay visible. The later row is not dropped, and the first is not overwritten. The conflict record shows both observation dates, not only the amounts. Neither value is copied into the ledger.

Freshness uses the caller-supplied as-of date and maximum age. It does not read the wall clock. Fresh means the observation date is on or before as-of, the retrieval date is on or before as-of, and as-of minus the observation date is within the maximum age. Otherwise the flags include `stale`, `future_observation`, or `future_retrieval`. A missing value is not fresh and is not zero.

`assess(store, as_of)` returns limitations only: synthetic fixture, stale, conflict, source not connected, and excluded social source, when each one applies. It has no recommendation field and no probability.

## Open the page

From the checkout root, `python scripts/serve_prototype.py` binds `127.0.0.1:8765`. Open `http://127.0.0.1:8765/evidence`. The desk navigation links to that path. `?date=YYYY-MM-DD` selects the desk date used for freshness. The default is the latest book date.

The page says the desk is in research mode and that the page is not a recommendation. It shows each source as connected, prepared, blocked, or excluded. Norges Bank, the ECB, and Statistics Norway are connected. Statistics Norway is connected for table 14700 cell 2026M07 total. Other SSB tables remain unconnected. SEC EDGAR is prepared. FRED is blocked. Social is excluded. Each connected source is also printed as current or due. `due_status` looks only at stored observations and the page date. A connected source is current when it has one non-synthetic observation whose freshness is fresh. Otherwise it is due. Synthetic fixture rows do not make a source current. The function does not fetch and does not start a loop. When the ingest cache has a retrieval timestamp, the page shows that last refresh time. Otherwise it says no live refresh has been stored. It shows freshness, provenance, any stored error, and revision records when they exist. An identical refresh does not add another revision record. Ingested USD/NOK points are an inline SVG of stored observations. Missing dates are not interpolated. Recorded points and live points are labeled differently when both exist. The synthetic 10.25 fixture stays labeled synthetic and is not drawn as a Norges Bank point. NOWA is not drawn on the USD/NOK chart. Stored policy-rate points use the same chart rules. The synthetic 4.50 fixture stays labeled synthetic and is not drawn as a live Norges Bank point. Stored NOWA points use those same marker rules on an inline SVG with id `nowa-ingested`. Missing dates are not interpolated. The synthetic policy fixture, USD/NOK points, and EUR/NOK points are not drawn on that chart. For each observation date that has both `nb-exr-EUR-NOK-{date}` and `ecb-exr-NOK-EUR-{date}`, the page shows both values and the arithmetic difference Norges Bank minus ECB, computed with Decimal and rendered with `format(value, 'f')`. It says: "This difference is not a recommendation and is not copied into the ledger." If only one side exists, the pair is incomplete and no difference is printed. Neither rate is inverted. `POST /evidence/refresh` is a manual refresh for the six requests, not a scheduler. These observations do not change `Ledger.value`.

When `ssb-cpi-total-2026M07` is visible, the page includes this sentence: "The CPI date is the first day of 2026M07. Stale in October means the monthly index is older than 7 days. It is not a failed daily refresh." The observation date is 2026-07-01 because 2026M07 is stored as the first day of that month. Against 2026-10-11 and a 7-day window the row is stale. The freshness rule is unchanged. The page does not mark that row fresh.

The page lists each stored subject once in a section titled Stored series. Each line shows the source id, the latest observation date among visible rows for that subject, and the value on that latest date. If two rows share the latest date, the line shows both values and says the date has more than one row. The inventory is computed from stored rows only. When both kinds are stored, it says rows marked `live_retrieval` were read from the public source, rows marked `synthetic_fixture` were not, and neither kind supports a recommendation.
